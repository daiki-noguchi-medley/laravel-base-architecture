# review-pr

PR の差分を、このリポジトリのサブエージェントでレビューする。

⚠ 上の `allowed-tools` は **手元で `/review-pr` を呼んだときの許可**。CI での許可は
`.github/workflows/claude-code-review.yml` の `claude_args` にある `--allowedTools` が一次情報で、
そちらでは **Bash を一切許可していない**。
ここに長いツールパターンの列を書くとスキル自体が読み込めなくなり、
指示を失った状態で走ってしまう。**増やさない。**

**指摘の中身の基準はサブエージェント側が持つ。** このスキルが決めるのは
「誰を起動するか」「どう束ねるか」「どこに書くか」だけ。
規約そのもの (レイヤー・命名・型付きクラス・enum の置き場など) は
ルートの `CLAUDE.md` が一次情報で、それを検査するのは `laravel-code-reviewer` の仕事。
**ここに規約を書き写さない** (二重管理になり、必ずずれる)。

⚠ **CI で動くのは «base (main) 側» のこのファイル。** `claude-code-action` は実行前に
`.claude/` を base の内容へ戻す。PR HEAD が信頼できない入力だからで、正しい挙動。
つまり **このスキルやエージェント定義を変える PR では、その変更はまだ効かない**
(マージ後から効く)。PR で «追加した» 体はその PR では起動できないので、
**その体の担当ぶんは人が読むしかない**。summary にその旨を必ず書く。

## 1. 差分を読む

CI では前段のステップが次のファイルを用意している。まずこれを読む。

| パス | 中身 |
|---|---|
| `.claude-review/changed-files.txt` | 変更されたファイルのパス一覧 (リポジトリルート相対) |
| `.claude-review/diff.patch` | base との差分 (unified diff) |
| `.claude-review/pr.json` | PR の番号・タイトル・本文・作成者・base/head ブランチ・URL |
| `.claude-review/base-sha.txt` | 差分の起点コミット |
| `.claude-review/existing-comments.json` | すでに付いている inline コメント |

⚠ **CI ではこの 5 ファイルが差分の一次情報。Bash は一切使えない。**
`git` も `gh` も許可されていないので拒否される。取り直す理由も無い (同じ差分をもう一度引くだけ)。
サブエージェントも同じで、**PR 本文が要る体 (`laravel-migration-pr-checker`) は
`.claude-review/pr.json` を `Read` する** (定義には `gh pr view` と書いてあるが、CI では通らない)。
読み取り系だけを許す形も採らない — `git diff --no-index /dev/null <パス>` で任意のファイルが読め、
`git diff --output=<パス>` で書き込みまでできるため。

手元で呼ばれてファイルが無いときだけ `git diff --name-only origin/main HEAD` と
`git diff origin/main HEAD` で同じものを作ってから進める。

PR 本文 (`pr.json` の `body`) は必ず読む。**レビューの精度は本文の説明に依存する**し、
本文で「意図的にこうした」と理由が書かれている点を指摘し返すのは無駄なので、そこは指摘しない。

## 2. サブエージェントを選ぶ

変更ファイルの種別で決める。該当するものは **すべて並列で起動する**
(Task を同一メッセージで複数呼ぶ)。

⚠ **Task は `run_in_background: false` で呼ぶ。** 既定では background 実行になり、
親のターンが先に終わったところでセッションが畳まれて «起動したのに結果が返らない» が起きる。
同一メッセージで複数呼べば並列に走ることは変わらない。

| 変更ファイル (拡張正規表現) | 起動する体 | 何を見るか |
|---|---|---|
| `^src/(app\|Demo)/.*\.php$` / `^src/resources/views/` | `laravel-code-reviewer` | 規約 (命名・レイヤー・型付きクラス・enum・Blade) |
| `^src/database/migrations/` | `laravel-migration-pr-checker` | PR 本文の記載要件 (CLAUDE.md §9) |
| `^src/resources/js/` | `frontend-reviewer` | React / htmx のお作法とコード衛生 |
| `^\.github/` / `^\.claude/` | `github-actions-reviewer` | 起動条件・権限・失敗の握り潰し・固定と更新 |
| `^src/(app\|Demo\|config\|routes\|bootstrap)/` | `security-ops-reviewer` | 秘密情報・セッション・外部連携・ジョブの運用 |

⚠ **この表を増やしたら、`.github/workflows/claude-code-review.yml` の
「担当がいるのに起動していない」判定にも同じ対応を反映する。**
2 箇所に持つのは本来よくない (片方だけ直すと黙ってずれる)。
体が増えて表が育ったら、**`.github/reviewers.json` のような 1 ファイルへ切り出して
両方がそれを読む**形にすること。

どれにも当たらない場合 (ドキュメントのみ、`docker/` のみなど) はサブエージェントを起動せず、
「この差分に対応するレビュワーが無い」ことを summary に 1 行書いて終わる。
**無理に汎用レビューをしない。**

⚠ **ワークフローの «構文・非推奨コマンド・action の固定漏れ» は指摘しなくてよい。**
CI の «ワークフローの検査» ジョブ (`.github/workflows/ci.yml`) で `actionlint` と `zizmor` が
毎回見ており、外れていればそちらが赤になる。

### 各サブエージェントに渡す指示

1 体ごとに、次を必ず含めて渡す。

- 対象の PR 番号・タイトル・本文の要点
- **そのサブエージェントが担当する変更ファイルのパスだけ** (担当外を渡すと指摘が散る)
- 差分は `.claude-review/diff.patch`、変更後の全文はワークツリーの実ファイルを読めばよいこと
- **差分に現れていない箇所を指摘しないこと** (PR の範囲外は扱わない)
- 推測で書かないこと。コードから確認できた事実だけを指摘すること
- 担当分を見切れなかった場合は、**何をどこまで見て、なぜ見切れなかったか** を末尾に書くこと

⚠ **出力形式をこちらから指定しない。** 各体は自分の定義 (`.claude/agents/*.md` の
「## 出力フォーマット」) に Markdown の書式を持っている。ここで JSON など別形式を要求すると、
エージェント自身の指示と競合してどちらで返るか不定になる。**返ってきた Markdown をこちらが読む。**

## 3. 束ねる

- **二重フィルタ**: サブエージェントが挙げた指摘のうち、
  あなた自身が読んでも «実際に直すべき» と判断できたものだけを採用する。
  根拠が差分から確認できないものは落とす
- 同じ箇所に複数のサブエージェントが同趣旨の指摘をしたら 1 件に統合する
- **深刻度は採用するときにあなたが付ける** (各体は深刻度を持たない書式で返す)
  - `P0` … 落ちる・壊れる・漏れる
  - `P1` … 規約違反、実害のある設計崩れ (各体が `[重大]` / `[要修正]` と書いたものは概ねここ以上)
  - `P2` … 直した方がよい
  - `P3` … 好みの範囲
- サブエージェントが «見切れなかった» と書いてきたら、その事実を summary に必ず残す。
  **黙って «指摘なし» にしてはいけない** (動いていないのと区別が付かなくなる)

## 4. 投稿する

- 採用した指摘を inline comment として該当行に付ける。
  **上限 10 件**、`P0` → `P1` → `P2` の順に選ぶ。
  `P3` と溢れた分は inline にせず summary にまとめる
- 行を指定できるのは差分に現れている行だけ。ずれる場合は inline を諦め、
  summary に `ファイル:行` を書いて指摘する
- **そのまま置き換えれば直るものは suggestion で出す。**
  指摘された側がボタン 1 つでコミットできる

  ````markdown
  P1 日時は `CarbonImmutable::now()` で取る (`CLAUDE.md` §6)。裸の `now()` は使わない。

  ```suggestion
          $createdAt = CarbonImmutable::now();
  ```
  ````

  ⚠ **suggestion は指定した行範囲を «丸ごと» 置き換える。** 守ること:
  - **インデントを含めて、置き換え後の行の全文** を書く (差分の `+` / `-` は付けない)
  - 1 行なら `line` だけ、複数行なら `startLine` と `line` の両方を渡す。
    **渡した範囲とブロックの中身が 1 対 1 で対応していること。**
    範囲より短く書くと、余った行が消える
  - 置き換えた結果がそれ単体で通ること (閉じ括弧・セミコロン・必要な `use` の有無)
  - 付けられるのは差分の **変更後 (`side` は既定の `RIGHT`)** の行だけ
- **suggestion にしないもの** — 設計の作り直し、複数ファイルにまたがる修正、
  どちらの案もありうるもの、周りの行を読み直さないと直せないもの。
  無理に形にすると «適用したら壊れる» 提案になる。**その場合は文章で書く**
- ⚠ **`.claude-review/existing-comments.json` を先に読み、同じ箇所に同趣旨の指摘が
  すでに付いていたら再掲しない。** sticky comment が束ねるのは summary だけで、
  inline は再レビューのたびに積み上がる。抑えた件数は summary に 1 行で書く
- ⚠ **サブエージェントの結果を受け取った時点で終わらないこと。** 束ねて、投稿して、
  summary を «進行中» ではない最終の形に書き換えるまでが 1 回のレビュー
- ⚠ **最終の summary に未チェックのチェックボックス (`- [ ]`) を残さない。**
  CI 側はこれを «やりきっていない» 印として赤にする。
  ⚠ 逆に **進行中の summary には `- [ ]` を 1 つ以上入れる**。この 2 つは対で、
  «束ねる前に落ちた実行» を CI が赤にできるのは進行中の本文に必ず残るからこそ。
  直してほしいことを列挙するときは箇条書き (`-`) を使う
- 最後に summary を出力する (これが PR の sticky comment になる)。次を含める。
  1. 起動したサブエージェントと、それぞれが見切れたかどうか
  2. 深刻度ごとの件数
  3. inline に載せた指摘の一覧 (1 行ずつ)
  4. `P3` / 溢れた指摘
  5. 指摘が無い場合は「見た範囲と、無かったこと」を書く (空の summary にしない)
- 文章は日本語。**PR 上の文章に個別のレビュー支援ツール名を書かない** (`CLAUDE.md` §13)。
  サブエージェント名 (`.claude/agents/` にあるもの) は共有物なので書いてよい
